# MR NEON API Security Policy — Wave 3

## Default policy

1. Deny by default: only explicitly registered Action names and HTTP methods are recognized.
2. The active routes are `getSession`, `login`, `adminLogin`, and `logout`. All other registered legacy routes stay closed until the respective Wave 4–6 implementation and tests are accepted.
3. Authorization is enforced on the server; UI visibility and client-supplied IDs/roles are never permissions.
4. Same-origin is the default. No arbitrary Origin reflection or credentialed wildcard CORS is used.
5. Cookie-based mutations require session-bound CSRF validation and compatible origin/fetch-metadata checks.
6. DB-backed login rate limits fail closed on dependency errors. Disabled legacy routes do not write to `data/rate_limits.json` before returning an intentional error.
7. Errors are represented with RFC 9457 `application/problem+json`; responses do not expose raw exceptions, SQL, DSN, file paths, hashes, session IDs or secrets.
8. Request IDs are generated by the server and appear in response metadata/headers and sanitized error logs.
9. First-party JavaScript transport is centralized in `js/api-client.js`. It enforces same-origin, uses same-origin credentials, attaches CSRF, validates content type and response envelope, and does not automatically retry mutations.
10. No API key, bearer credential, password or session token is stored in Local Storage or Session Storage. Legacy Authorization headers are stripped by the compatibility adapter.

## Authorization matrix summary

- Public/read-only: `getSession`.
- Public authentication flows with CSRF: `login`, `adminLogin`, `register`, verification and recovery routes. The latter are not implemented and fail closed until Wave 4.
- Authenticated customer only: project, customer message, notification, profile and NEO routes. In Wave 3 these are not implemented and fail closed after required customer session/CSRF checks.
- Administrator only: admin list/update/delete-request routes. In Wave 3 these are not implemented and fail closed after independent admin session and CSRF checks.
- System/CLI-only operations such as migrations are outside this HTTP Action router and remain guarded by CLI bootstrap.

See `WAVE-3-ACTION-MATRIX.csv` in the report bundle for the complete 27-action policy.

## Production blockers

- Database integration suite must be run against an isolated MariaDB/MySQL version supported by deployment.
- Admin TOTP recovery codes or an approved equivalent need secure persistence and successful tests.
- Admin user lifecycle/multiple-admin requirements remain an owner decision.
- Real host Web Root, HTTPS termination, trusted-proxy configuration, DB TLS, secure env injection, restore, and Browser E2E must be verified against the selected production host.
- Registration/OTP/Recovery and all domain API handlers remain intentionally blocked until their own Waves.
