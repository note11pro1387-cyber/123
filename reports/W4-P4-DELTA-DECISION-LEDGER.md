# W4-P4 Delta Decision Ledger

| ID | Decision | Evidence / Rationale | Impact / Follow-up |
|---|---|---|---|
| P4-D01 | Reuse W4-P3 transport/result types; no parallel OTP/challenge service. | Existing W4-P3 source and handoff establish a typed in-memory delivery envelope and `accepted/rejected/unknown/not_configured`. | P3 remains source of truth for OTP HMAC, Challenge lifecycle, TTL and Completion. |
| P4-D02 | Telegram link uses existing `registration_attempts.telegram_link_nonce_hash`; no new Migration. | Migration 004 already has nonce hash, linked Telegram user/chat IDs and linked timestamp; nonce can be cleared atomically after proof. | No schema delta. Integration still requires disposable MariaDB/MySQL test. |
| P4-D03 | Reuse `idempotency_keys` to bind Telegram `update_id` to canonical request hash. | Migration 014 has unique scoped route key and request hash/state. | Same update/payload becomes no-op; same update ID with changed body is never reapplied. |
| P4-D04 | Expose Bot deep link only when a valid Bot username/token, independent webhook secret and public HTTPS base URL are configured. | A 64-character random hex value fits Telegram's documented `/start` parameter limit; local HTTP/localhost is not a public webhook. | Attempt stays pending when config is absent; no raw nonce is exposed as a separate response field. |
| P4-D05 | Telegram target is only the linked private-chat ID loaded by W4-P3; admin chat fallback is forbidden. | The P3 service resolves Telegram targets from `linked_telegram_user_id` and `linked_telegram_chat_id`. | Provider rejection/unknown never activates a challenge. |
| P4-D06 | SMTP supports authenticated `STARTTLS` or `SMTPS` only, with peer/certificate checks always enabled. | Runtime has OpenSSL but no Composer, PHPMailer or existing `composer.json`; no dependency manager/vendor tree was introduced implicitly. | Limited SMTP subset: AUTH LOGIN; real SMTP provider acceptance test remains a release gate. Consider PHPMailer if a managed Composer workflow is adopted. |
| P4-D07 | Webhook registration is explicit CLI only and preserves pending updates. | Owner has not established a final public domain/HTTPS endpoint. | Manual `set`/`delete`/`info` runbook; not executed here. |
| P4-D08 | Owner's database Integration deferment stays open and not PASS. | Current runtime reports no PDO drivers and no MySQL server. | W2/W3/W4-P3/W4-P4 DB Integration remains for final test window. |
| P4-D09 | UI minimally displays Telegram link and a CSRF-protected boolean status check. | Existing auth flow already has an Attempt ID and user-selected channel; it otherwise attempted OTP before link completion. | No Tailwind/Vite or broad UI redesign. |
| P4-D10 | A Telegram identity already linked to an Attempt is immutable; idempotent registration retry must not issue a fresh linking nonce. | Repository compare-and-consume conditions now require all linked identity fields to be NULL; RegistrationService returns the existing `telegramLinked` state; the UI shows the state rather than presenting a fresh link. | Prevents account/destination swap on a reused Attempt. MySQL behavior is covered by a guarded Integration runner but remains BLOCKED in this runtime. |
| P4-D11 | Provider/client secret-bearing objects are not serializable and debug output is redacted. | `TelegramBotApiClient` and `SmtpConfiguration` override debug/serialization behavior; Unit assertions verify it. | Reduces accidental leak through generic diagnostics. |
| P4-D12 | Real SMTP integration is a separate manual opt-in. | No SMTP credentials/inbox was available; added a guarded runner which requires explicit opt-in and a configured test inbox. | No email sent in this environment; final acceptance of a live SMTP server remains a release check. |

| P4-D13 | Keep email dependency footprint unchanged for this Patch, but record the native SMTP client as a production risk. | Official PHPMailer release list identifies v7.1.1 as latest (checked 2026-10-12) and official docs recommend a maintained library; inspected project has no Composer workflow and the runtime could not retrieve the full official package for integrity-checked integration. | Before production, adopt PHPMailer through an approved dependency workflow or complete an independently reviewed, integrity-checked official source integration, then run a real SMTP acceptance test. |

| P4-D14 | Telegram HTTP 408 and 5xx responses are `unknown`, not definite rejection. | These server/gateway outcomes do not prove `sendMessage` was not accepted; Unit tests cover this mapping. | Avoid blind retries and duplicate OTPs; reconcile uncertain delivery first. |
